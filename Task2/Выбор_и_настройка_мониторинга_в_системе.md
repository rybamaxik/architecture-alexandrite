**Мотивация**

Мониторинг даст возможность инженерной команде значительно улучшить знания о том, 
какое количество запросов в среднем и в максимуме поступает на сервисы системы,
какие части системы испытывают повышенную нагрузку, в каких частях системы и в 
какие моменты времени показатели (метрики) функционирования становятся ненормальными.

Также это позволит инженерной команде выполнить анализ нагруженности системы 
в зависимости от временнЫх периодов, что может в дальнейшем помочь экспертной 
системе, ML-модели или аналитикам делать предсказания по нагрузке в различные 
моменты времени. Наконец, это позволит инженерной команде правильно выставить 
приоритеты по модернизации системы, выполняя оптимизацию самых нагруженных 
сервисов в первую очередь.

**Выбор подхода к мониторингу**

Если бы нужно было выбрать единый подход к мониторингу, то в этом случае наиболее 
уместным был бы подход "четыре золотых сигнала" от Гугла. Он хорошо подходит для
мониторинга системы в целом.

Но лучше выбрать раздельные подходы к мониторингу разных частей системы:

для Shop API, CRM API, 3d files storage - метод RED (замеряет основные показатели 
"счастья" пользователей)

для MES API, Message Queue, MES DB и Shop DB - метод USE (замеряет основные показатели 
"счастья" машин)

MES API мы отнесли к методу USE, потому что по характеру его работы это больше похоже 
на некий условный "сервер", учитывая длительность обработки запросов. Однако, поскольку 
этот микросервис принимает запросы от внешних акторов, то для него включим в мониторинг 
также и привычные для RED показатели (количество запросов в секунду, и т.п.). Кроме того, 
чтобы оценить объем трафика для 3D-моделей, включим также показатели количества трафика.

**Список метрик**

для Message Queue:
- Number of dead-letter-exchange letters in RabbitMQ , чтобы определить, как много 
  сообщений не дошло до адресата вовремя или из-за переполнения очереди 
  (например, CRM API "забывает" их забрать);
- Number of message in flight in RabbitMQ , чтобы определить, как много сообщений 
  находится во всех очередях (если их стало сильно больше при отсутствии нагрузки, 
  то это аномалия);

для Shop API:
- Number of requests (RPS) for internet shop API;
- Number of requests (RPS) per user for internet shop API;
- Response time (latency) for shop API;
- Number of HTTP 200 for shop API;
- Number of HTTP 500 for shop API;
- Number of simultanious sessions for shop API.

для CRM API:
- Number of requests (RPS) for CRM API;
- Number of requests (RPS) per user for CRM API;
- Response time (latency) for CRM API;
- Number of HTTP 200 for CRM API;
- Number of HTTP 500 for CRM API;
- Number of simultanious sessions for CRM API.

для MES API:
- Number of requests (RPS) for MES API;
- Number of requests (RPS) per user for MES API;
- CPU % for MES API;
- Memory Utilisation for MES API;
- Response time (latency) for MES API;
- Number of HTTP 200 for MES API;
- Number of HTTP 500 for MES API;
- Number of simultanious sessions for MES API;
- Kb tranferred (received) for MES API;
- Kb provided (sent) for MES API;

для MES DB:
- Memory Utilisation for MES db instance;
- Number of connections for MES db instance;
- Size of MES db instance;
- Утилизация дисков (количество операций чтения/записи на диски 
  в секунду (disk IOPS), объем данных для чтения/записи на диски
  в секунду).

для Shop DB:
- Memory Utilisation for shop db instance;
- Number of connections for shop db instance;
- Size of shop db instance;
- Утилизация дисков (количество операций чтения/записи на диски 
  в секунду (disk IOPS), объем данных (MB/s) для чтения/записи на диски
  в секунду).

для S3 storage:
- Size of S3 storage;
- величина пинга в миллисекундах к внешнему серверу S3 storage и количество 
  потерянных пакетов.

Для Shop API, CRM API, MES API мы включили основные показатели RED (Requests rate, 
Errors, Duration). Думаю, расписывать их не имеет особого смысла, по названию 
прекрасно понятно, когда речь идет о количестве запросов со стороны пользователей, 
когда - о количестве успешных ответов и ответов с ошибкой, и т.п.

Для MES API (вдобавок к RED), MES DB, Shop DB и S3 storage включили показатели USE.
Утилизация памяти и дисков позволяет отследить проблему перегрузки того и другого, 
что приводит обычно к самым серьезным проблемам производительности, времени отклика 
и т.д. Переполнение памяти приводит к своппингу и катастрофически медленной работе, 
перегрузка дисков тоже приводит к крайне медленной работе БД.

Для баз данных (особенно на основе PostgreSQL), кроме этого, также крайне важно 
количество одновременных соединений (исчерпание их лимита приводит к 
невозможности присоединиться к БД).

Для S3 storage сложно придумать разумные метрики. С учетом нынешних проблем 
со связностью сетей крайне важно отслеживать пинг к фронт-серверам хранилища.

**План действий**

1. На отдельном VPS (желательно в том же дата-центре, где развернуты основные сервисы) 
разворачиваем инстансы Prometheus и Grafana - либо с помощью docker-compose, либо 
(если мы уже дошли до автоматизации деплоя) с помощью Kubernetes и Helm.

2. Дополняем код сервисов поддержкой эндпоинтов, которые будут использоваться для 
отсылки показателей датчиков в Prometheus. Потребуется участие разработчиков, 
включая тех, кто будет внедрять отсылку метрик в MES API, что может стать проблемой 
из-за проприетарности этого продукта.

3. Прописываем в инстансе Prometheus источники метрик в виде вышеуказанных эндпоинтов.

4. Устанавливаем также на всех виртуалках, где запущены какие-либо сервисы или БД, 
модули Prometheus Node Exporter, прописываем в инстансе Prometheus получение данных 
от них. Этот экспортер нужен для получения системной информации типа нагрузки на CPU, 
утилизация памяти, и т.п.

5. Устанавливаем также специфические экспортеры: для Message Queue - Prometheus 
RabbitMQ exporter, для Shop DB, MES DB - Prometheus PostgreSQL exporter.
Настраиваем Prometheus для получения метрик от них.

6. На инстансе Grafana заводим дашборды с выбранными ранее показателями для каждого 
сервиса. Кроме того, заводим общие для всех причастных сервисов дашборды по 
основным показателям - например, дашборд для задержек обработки запросов 
по метрикам от всех сервисов, дашборд с количеством одновременных сессий, дашборд 
по количеству запросов в секунду по метрикам от всех сервисов, и т.д.

7. Анализируем полученные данные.
