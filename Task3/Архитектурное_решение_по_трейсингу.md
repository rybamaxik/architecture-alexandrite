**Трейсинг**

В первую очередь будем покрывать трейсингом все сервисы, принимающие запросы, то есть, Shop API, CRM API, MES API.
Далее также покроем трейсингом Shop DB, MES db и Messages Queue.

Данные, которые должны попасть в трейсинг со стороны API:
- идентификаторы пользователей (customer), продавцов (seller), пользователей API (API user), операторов;
- идентификаторы заказов (order id), 3d-моделей (3d file id);
- статусы заказов и таймстампы, соответствующие изменениям статусов.

**Мотивация**

Для чего нам нужен трейсинг?

- чтобы понять, где именно заказ подвисает на долгое время;
- чтобы понять, где заказ теряется;
- чтобы иметь возможность отследить все этапы прохождения заказа без необходимости писать логику отслеживания 
в разных сервисах.

На какие метрики положительно повлияет внедрение трейсинга:

- качество техподдержки (среднее время решения проблемы по тикету);
- прозрачность потоков данных;
- наблюдаемость состояния заказов;
- более полная статистика запросов от внешних акторов.
- улучшение качества кода после исправления багов, выявленных по результатам анализа трейсинга.

**Предлагаемое решение**

Силами программистов бэкенда предлагается реализовать передачу телеметрии во всех обработчиках входяших 
вызовов API во всех трех сервисах API (Shop, CRM, MES). Для передачи телеметрии задействуем OpenTelemetry SDK.
Также программисты должны обернуть в телеметрию работу сервисов с Shop DB и MES db.

DevOps на отдельном VPS разворачивает инстанс Jaeger+Jaeger UI, настраивает сервисы на передачу туда 
телеметрии. Для хранения данных трейсинга DevOps разворачивает также БД PostgreSQL.

Тимлид настраивает дашборды в Jaeger UI.

Сразу после включения сбора телеметрии тимлид организует совместно с QA и продакт-менеджером процесс поиска 
зависших заказов, строго по необходимости подключая бэкендеров для прояснения неочевидных моментов.

**Компромиссы**

Трейсинг может не принести пользу, если:

- он не будет охватывать все вышеперечисленные в начале документа сервисы;
- не будет обеспечена полнота трассировки по данным, перечисленным выше;
- тимлидом не будет налажена системная работа по разбору трассы как проблемных заказов, так и 
выборочно беспроблемных;
- не будет проверена/протестирована полнота собираемых трейсингом запросов извне.

Трейсинг может быть тяжело внедрять в MES API, так как этот сервис был написан вне команды.

Также может выдаться достаточно затратным по времени и усилиям разработчиков обеспечить полноту 
трассировки.

Наконец, существует возможность внедрить трейсинг также и в MES db, Shop DB и Messages Queue. 
Например, в тексты запросов можно добавлять комментарии с идентификаторами trace_id и span_id .
В тело сообщений, которые проходят через Messages Queue, также можно добавить эти идентификаторы.

Однако, эти меры могут не принести пользы, при этом они довольно трудозатратные - для PostgreSQL
не существует стандартизированного (хотя бы в рамках OpenTelemetry) способа внедрить идентификаторы.
Покрывать же трейсингом обмен сообщений через Messages Queue - это означает, что количество данных, 
которые будут попадать в БД трейсинга, будет примерно того же порядка, что и суммарный объем всех 
сообщений, что скорее всего вызовет перегрузку сервера БД трейсинга.

Поэтому трейсинг в MES db, Shop DB и Messages Queue себя скорее всего не оправдает. Проблемы с 
этими компонентами можно идентифицировать через мониторинг и анализ логов.

**Аспекты безопасности**

- настройка аутентификации (доступ к данным, собранным через трейсинг, имеют только разработчики, 
  QA и тимлид);
- исключение охраняемых законом персональных данных пользователей из трейсинга, применение вместо 
  них специальных идентификаторов;
- доступ к Jaeger UI должен быть ограничен локальной сетью компании.
