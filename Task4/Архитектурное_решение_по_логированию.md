**Что мы будем логировать**

Мы будем собирать логи работы следующих модулей:

1. от Internet Shop, CRM и MES - логи веб-сервера (например, nginx) уровня INFO. Данные, 
которые нас интересуют - URL запроса, возвращенные клиенту коды ошибок HTTP, IP-адреса 
клиентов, данные user agent. таймстампы. Также возьмем логи системного журнала (dmesg) 
тех серверов и/или VPS, где запущены веб-серверы.

2. от Shop API, CRM API, MES API - логи изменения состояния заказа, всех запросов/вызовов API.
Кроме состояния заказа, логируем идентификаторы заказов, клиентов, продавцов, 3D-моделей, 
таймстампы (точное время) запросов. Вполне возможно, что для MES API будут в дальнейшем 
использоваться логи более подробного, чем INFO, уровня, так как код в основном написан за 
пределами команды, поэтому вполне вероятно, что потребуется более подробное логирование для 
того, чтобы разобраться в происходящем. Также возьмем логи системного журнала (dmesg) со всех 
серверов и/или VPS, где работают эти сервисы.

3. от Shop DB, MES db, Messages Queue - логи с текстами запросов с длительным временем выполнения, 
логи с текстами запросов, завершившихся ошибкой, логи запросов, вызывающих откат транзакции, 
логи работы БД и очереди от уровня INFO в сторону более важных. И снова берем логи системного 
журнала (dmesg) со всех серверов и/или VPS, где работают эти сервисы.

Допускается также введение более подробного логирования на сервисах DB и/или Queue, если 
анализ логов и мониторинг покажет в сторону этих сервисов как источников проблем.

**Мотивация**

Зачем нам логирование? Как и в случае с трейсингом, это позволит нам в конечном итоге лучше 
понять, что происходит с системой в целом через улучшение наблюдаемости отдельных ее 
компонентов. Мы не можем использовать отладку на боевом окружении - это очень дорого, 
неэффективно, и ставит под риск комплиментарность наших клиентов. Через грамотно выстроенное 
логирование мы можем собрать всю необходимую нам информацию о происходящем, что позволит 
разработчикам точно идентифицировать и исправить как ныне имеющиеся проблемы, так и те, 
о которых мы узнаем в будущем. Более того, через анализ логов мы можем даже узнать о проблемах 
раньше, чем с ними столкнутся наши клиенты.

Кроме того, анализ логов компонентов системы, находящихся на периметре, - то есть, тех, 
с которыми непосредственно работают клиенты и вообще внешние акторы, - позволит также 
начать большую и крайне важную работу по сборку статистики - для формирования статистических 
профилей наших клиентов, их предпочтений, графиков активности, и т.п. Без анализа логов 
решить эти задачи с приемлемым качеством практически невозможно.

Наконец, анализ логов позволит идентифицировать DDOS-атаки в самом их начале, улучшит 
шансы на продуктивное расследование инцидентов, связанных с взломами и злонамеренной 
активностью.

Ведение и анализ логов позволит:
- улучшить наблюдаемость и прозрачность процессов внутри системы, взаимодействие ее 
  компонентов друг с другом;
- уменьшить время простоя, т.к. идентификация причины багов не потребует отладки на боевом 
  окружении;
- снизить среднее время отклика по баг-репортам и жалобам клиентов;
- улучшить формирование статистических профилей клиентов, сделать анализ активности;
- укрепить безопасность системы и в конечном счете устойчивость к атакам извне.

Поскольку одновременно покрыть трейсингом и настроить логирование во всех компонентах 
одновременно не получится, предлагаю в первую очередь покрыть трейсингом API-компоненты 
(MES API, Shop API, CRM API - в таком порядке) и одновременно настроить логирование 
в Internet Shop, CRM, MES, Shop DB и MES db. Трейсинг с таймстампами позволит нам 
оценить скорость и ошибки в прохождении заказов через системы, логирование баз данных 
позволит идентифицировать проблемные запросы (долго выполняющиеся или откатывающие 
транзакции). Логирование веб-сервера в Internet Shop, CRM и MES позволит взглянуть 
на ситуацию глазами клиентов сервисов, сопоставить ошибки сервисов, возвращаемые 
клиентам, с их запросами.

**Предлагаемое решение**

Силами разработчиков прорабатываем возможность в компонентах Shop API, CRM API и MES API 
включить достаточно подробное логирование. При необходимости модифицируем код, 
добавляя логирование вышеописанных важных данных в ключевых местах (эндпоинты API, 
взаимодействие с другими сервисами, изменение статуса заказов).

Параллельно с этим процессом, который может быть достаточно длительным, силами девопса 
в контейнер каждого сервиса, покрываемого логированием, добавляем компоненты Beats, 
а именно - FileBeat для сбора логов и MetricBeat для сбора таких метрик, как загрузка 
CPU, потребление RAM, утилизация дисков и сетевых адаптеров.

Также силами девопса в отдельном контейнере (на отдельном сервере или VPS) поднимаем 
сервисы Logstash, ElasticSearch и Kibana. Настраиваем Logstash - создаем пайплайны 
(по одному на каждый сервис) и настраиваем его на работу с ElasticSearch. Включаем 
также Kibana.

Настраиваем веб-сервер (nginx или другой) в сервисах Internet Shop, CRM и MES - включаем 
логирование с нужным нам набором полей (ip-адрес, user agent, URL запроса, поля HTTP).

Настраиваем логирование в MES db и Shop DB, а также в Messages Queue.

Настраиваем сервисы API на нужные уровни логирования (описано выше).

Настраиваем агенты Beats в каждом покрываемом логированием сервисе на отсылку логов и 
метрик в только что развернутый Logstash.

Через Kibana настраиваем ElasticSearch - создаем отдельные шаблоны индексов с маппингами 
полей для логов веб-сервисов, отдельно для каждого сервиса API, один для баз данных, 
один для Messages Queue. Создаем сами индексы, запускаем Logstash и Beats.

Индексы для логов баз данных, Messages Queue и веб-сервисов настраиваем на удаление 
после 1 месяца, остальных - после 6 месяцев. Если за месяц суммарный размер _остальных_ 
индексов превысит 100 Гб, то ElasticSearch будем шардировать на ноды, разделяющие логи 
по фазам, ноды размещаются на дополнительных VPS. При этом hot фаза будет 7 дней, 
warm фаза - 1 месяц, cold фаза - еще 5 месяцев.

Дальше совместно с тим-лидом настраиваем data view и дашборды. На дашбордах в первую 
очередь отображаем все события с любыми кодами ошибок.

В процессе настройки логирования убеждаемся в том, что личные данные клиентов 
не записываются в логи. Настраиваем доступ к Kibana только для QA, разработчиков, 
тим-лида.

**Анализ логов**

Настраиваем алертинг - по резким скачкам нагрузки CPU, использования RAM и дисков, 
по количеству запросов, приходящих на веб-сервисы и MES API за минуту, по скачкам 
среднего времени выполнения запросов в БД, по увеличению в логах количества запросов, 
вызывающих ошибку и откат транзакций в БД.
